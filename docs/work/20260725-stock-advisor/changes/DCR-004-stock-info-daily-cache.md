# DCR-004: ka10001 일 1회 캐시 + 당일 일봉 갱신

- 상태: **승인 (2026-09-23)** — 구현 대기
- 날짜: 2026-09-23
- 대상 기준선: design.md §5.1 시장 스캔 파이프라인 (v1), §4.1 TR 매핑, 데이터 모델
- 대체 관계: **DCR-003의 전제를 무효화**(아래 "무효화된 전제" 참조). DCR-003의 결정(랭킹 1페이지)은 유지한다.
- 배경 이슈: plan.md "스캔 1회 소요가 5분 28초 → 31~55분으로 악화, AC-19 깨짐"

## 배경

장중 스캔 1회가 **26~59분**으로 늘어 10분 주기가 무너졌다. 2026-09-23 실측:

```
09:01 시작 → 09:27 완료   26분  (후보 163)
09:31 시작 → 10:16 완료   45분  (후보 353)
10:21 시작 → 11:14 완료   53분  (후보 365)
11:21 시작 → 12:07 완료   46분  (후보 394)
12:11 시작 → 13:01 완료   50분  (후보 398)
13:11 시작 → 14:10 완료   59분  (후보 406)
```

14:37까지 완료된 스캔이 6회뿐이다. AC-19(스캔 1회가 주기 안에 완료)가 깨져 있고, 추천 갱신이
설계 의도(10분)의 1/5 수준인 시간당 1회꼴로 떨어졌다.

## 측정으로 확인한 사실 (2026-09-23)

**원인은 `ka10001`(주식기본정보)의 서버 응답 지연이며 우리 코드가 아니다.**

| 측정 항목 | 2026-08-04 기준선 | 2026-09-23 |
|---|---|---|
| `ka10001` 호출 간격 | 60~61회/분 = **콜당 1초 미만** | **중앙값 9.0초**(오전) → **15.0초**(오후), 최대 31초 |
| `ka10081` 호출 간격 | 54~61회/분 | 중앙값 1.0초 → 2.0초 |
| `유량 제한` 백오프 로그 | 간헐 발생 | **0건** (하루 종일) |
| 후보당 DB 쿼리 3종 | — | **1ms 미만** (운영 DB 사본 164MB, daily_price 168만 행) |

- 유량 제한 백오프 가설은 기각된다 — 하루 종일 `유량 제한` 로그가 한 건도 없다.
- DB 병목 가설도 기각된다 — `max(date)` 0.20ms, 20행 0.27ms, 250행 0.34ms.
- 163종목 × 약 10초 = 약 27분으로 첫 스캔 실측(09:01:06 → 09:27:45, **26분 39초**)과 일치한다.
- 코드는 2026-08-05 이후 변경이 없다. 서버 측 지연이다.

**구조적 증폭:** 클라이언트가 완전 순차 호출이라 서버 지연이 후보 수만큼 그대로 곱해진다.
게이트 상한(TR별 1회/초, 전역 5회/초)에는 여유가 많다.

### 무효화된 전제 (DCR-003)

DCR-003은 다음을 근거로 대안 E(캐싱으로 TR 축소)를 "시간 변화 없음"으로 기각했다.

> `ka10001`·`ka10081`이 서로 다른 TR 게이트(각 1회/초)를 쓰므로 후보 1건이 1초를 소비한다.
> TR 수를 줄여도 시간은 줄지 않으며 후보 수만이 지렛대다.

이 전제는 **게이트(1초)가 병목일 때만 성립**한다. 지금은 서버 지연(9~15초)이 게이트보다 훨씬 커서
병목이 게이트에서 서버로 옮겨갔다. 따라서 **`ka10001` 호출을 없애면 그만큼 벽시계 시간이 줄어든다.**
design.md §5.1의 "소요 시간 = 랭킹 수집 35초 + 후보 수 ÷ 60분" 공식도 함께 무효다.

### 조사 중 발견한 결함 — 당일 일봉이 갱신되지 않는다

`ingest_daily`는 DB의 최신 일자(`latest`) 이후 행만 저장한다. 당일 첫 스캔에서 오늘 행이 들어가면
`latest`가 오늘이 되어, **이후 모든 스캔에서 오늘 행이 `dt <= latest`로 걸러진다.**

결과:
1. 2회차 이후 스캔의 `ka10081` 응답은 **전량 폐기**된다(호출 비용만 지불).
2. 점수 계산에 쓰이는 `closes`·`volumes`가 **그 종목이 오늘 처음 스캔된 시점에 고정**된다.
   추천의 `base_price`도 마찬가지다.

실측 증거(2026-09-23 14:40 기준, 오늘 행의 거래량 ÷ 전일 거래량):

| 구분 | 종목 수 | 전일 대비 평균 |
|---|---|---|
| 09:01 스캔에 있던 종목 | 15 | **50.5%** (오전에 멈춤) |
| 14:11 스캔에 처음 들어온 종목 | 14 | **109.5%** (거의 전일 수준) |

갱신되고 있다면 두 집단이 비슷해야 한다. 장중 지표 신선도에 직접 영향을 주는 결함이다.

## 고려한 대안

후보 400종목 기준 예상 스캔 소요:

| 대안 | 예상 소요 | 위험·비용 | 판단 |
|---|---|---|---|
| **A. `ka10001` 일 1회 캐시** | 약 **10분** (후보당 `ka10081` 1~2초) | 장중 PER/PBR이 가격 변동분을 반영하지 않음 | **채택** |
| B. 상세 조회 동시 실행 | 약 6.7분 (TR별 1회/초 게이트가 상한) | 동시성 도입 — 게이트·재시도·순서 재검증 필요, 유량 초과 위험 증가 | 보류 — A 측정 후 재판단 |
| C. 후보 수 추가 축소 | 비례 감소 | DCR-003에서 이미 1페이지로 조임. 유동성 하한 상향은 추천 실적의 45% 구간 제거(DCR-003 근거) | 기각 |
| D. 스캔 주기 10 → 30분 | 변화 없음 | 문제를 주기 설정으로 덮는 것. 추천 신선도 저하를 확정 | 기각 |
| E. 장전 캐시 예열 잡 추가 | 첫 스캔도 빨라짐 | 예열 대상 종목 선정 기준이 필요하고 잡이 하나 늘어남 | 보류 — 후속 검토 |
| F. 조치 없이 서버 회복 대기 | — | 회복 시점을 통제할 수 없고, 그동안 추천이 시간당 1회 | 기각 |

**A를 먼저 하는 이유:** 호출 자체를 없애므로 효과가 확실하고, 동시성(B)보다 위험이 낮다.
A만으로 여유가 부족하면(예상 10분 = 주기와 동일) B를 별도 DCR로 올린다.

**`ka10001`을 캐시해도 되는 근거:** 이 TR이 스캔에 기여하는 값은 `per`·`pbr`·`roe`(long 프로파일의
value·quality)와 `crd_rt`(swing 프로파일의 risk)뿐이다. `stk_nm`은 랭킹 응답(`meta["name"]`)과
`instrument.name`에 이미 있다. PER·PBR은 가격에 연동되지만 장중 변동폭은 수 % 수준이고,
설계상 이 값들은 펀더멘털 지표로 다뤄진다.

## 결정

1. **`stock_info_daily` 캐시 테이블을 신설한다.** PK `(code, date)`, 컬럼 `per`·`pbr`·`roe`·`credit_ratio`.
   `build_candidate`는 오늘 날짜 행이 있으면 `ka10001`을 호출하지 않고 그 값을 사용한다.
   - 기존 `instrument` 테이블에 컬럼을 추가하지 않는다. 새 테이블은 `Base.metadata.create_all`이
     자동 생성하므로 **운영 DB 마이그레이션이 필요 없다**(기존 데이터 무영향).
   - 유효 기간은 상수로 박지 않고 설정(`scan.info_cache_days`, 기본 1)으로 둔다 — DCR-003의
     `scan.ranking_pages`와 같은 성격(실측으로 재조정 가능해야 한다).
2. **당일 일봉을 매 스캔 갱신한다.** `ingest_daily`에서 오늘 행은 건너뛰지 않고 갱신(upsert)한다.
   `ka10081` 호출이 2회차 이후 낭비되던 문제와 장중 지표가 고정되던 결함을 함께 해소한다.

## 요구사항·인수 조건

- **FR-26** 스캔의 종목 기본정보(PER·PBR·ROE·신용비율) 조회는 종목·거래일당 1회로 제한하고,
  같은 거래일의 이후 스캔은 저장된 값을 사용한다. 유효 기간은 설정으로 조정할 수 있다.
- **FR-27** 스캔은 당일 일봉을 매 스캔 갱신하여, 점수 계산에 쓰이는 종가·거래량이 해당 스캔 시점의
  값을 반영한다.
- **AC-20** 같은 거래일에 같은 종목이 두 번 이상 스캔될 때 `ka10001`이 1회만 호출된다.
- **AC-21** 2회차 이후 스캔에서 당일 일봉의 종가·거래량이 갱신된다(같은 종목의 오늘 행이 스캔 전후로 달라진다).
- **AC-22** 장중 스캔 1회가 주기(10분) 안에 완료된다 — 배포 후 다음 거래일 로그의 시작·종료 시각으로 확인.
  (AC-19의 재확인이며, 미달 시 대안 B를 별도 DCR로 올린다.)

## 마이그레이션과 롤백

- **마이그레이션 불필요** — 신규 테이블만 추가하므로 기존 `daily_price`·`instrument` 데이터에 영향이 없다.
- **롤백** — `scan.info_cache_days`를 `0`으로 두면 캐시를 쓰지 않고 종전처럼 매번 `ka10001`을 호출한다.
  코드 되돌림 없이 설정만으로 복귀 가능하다. 당일 일봉 갱신(결정 2)은 되돌릴 이유가 없는 결함 수정이다.

## 결과와 단점

- 장중 PER·PBR이 당일 첫 조회 시점의 가격 기준으로 고정된다. 가격이 크게 움직인 종목은 value 점수가
  실제와 어긋날 수 있다. 영향은 long 프로파일의 value(가중치의 일부)에 한정된다.
- **당일 첫 스캔은 여전히 느리다.** 캐시가 비어 있어 후보 전부가 `ka10001`을 호출한다
  (163종목 기준 약 27분). 장전 예열(대안 E)은 후속 검토로 남긴다.
- 캐시 테이블이 하루 수백 행씩 늘어난다(연간 약 10만 행). `daily_price`(168만 행) 대비 미미하다.
- 서버 지연이 회복되어도 캐시는 그대로 이득이다(호출 수 자체가 줄어 유량 여유가 커진다).
