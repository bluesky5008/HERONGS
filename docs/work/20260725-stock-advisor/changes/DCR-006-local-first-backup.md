# DCR-006: 로컬 우선 백업 — 컨테이너가 NAS를 붙잡지 않게

- 상태: **승인 (2026-09-30)** — 구현 대기
- 날짜: 2026-09-28
- 대상 기준선: requirements.md FR-19·AC-12, design.md §11.2·§11.4, `docker-compose.yml`, 부팅 스크립트(`~/.herongs-boot.sh`)
- 짝 변경: homeserver 저장소 **DCR-012**(NAS 동기화 작업 신설) · **ADR-013**(백업 전송 구조)

## 배경

HERONGS 백업이 2026-09-25~28 매일 `[Errno 17] File exists: '/backup'`으로 실패했다(텔레그램 경고 4회).
컨테이너는 NAS 폴더(`/Volumes/backup/herongs`)를 바인드 마운트로 붙잡는데, 호스트의 NAS 연결이 09-24 이후 끊기자
**죽은 마운트를 쥔 채 복구되지 않았다.** NAS 연결은 부팅 스크립트가 부팅할 때 한 번만 붙이므로 끊기면 그대로다.

같은 NAS를 쓰는 위키 백업은 macOS 권한 문제로 운영 개시 이래 한 번도 자동으로 올라가지 않았다(위키 DCR-012).
두 앱에 공통으로, **백업 생성과 NAS 전송을 분리**하는 구조로 바꾼다(위키 ADR-013).

## 결정

1. **컨테이너의 `/backup`을 로컬 `./backup`에 고정한다.** `docker-compose.yml`의 `${HERONGS_BACKUP_MOUNT:-./backup}`을
   `./backup`으로 바꾸고 `.env`의 `HERONGS_BACKUP_MOUNT`를 지운다. 백업 코드(`run_backup`, 03:00, 14일 보존)는 바꾸지 않는다.
2. **NAS 전송은 위키 저장소의 `nas-sync.sh`(매일 03:30)가 맡는다.** NAS 재연결 → 일회용 도커 컨테이너로 "NAS에 없는
   파일 전부" 복사 → NAS 쪽 14일 초과분 정리 → 실패 시 텔레그램 알림(이 저장소의 알림 봇 설정을 실행 시 읽음).
3. **부팅 스크립트에서 NAS 대기·폴백을 없앤다.** 컨테이너 기동이 NAS를 기다리지 않으므로 부팅 후 최대 4분의 NAS 대기와
   "NAS 실패 → 로컬 폴백" 분기가 필요 없다. 부팅 복구가 빨라지고 07-30에 겪은 부팅 순서 경쟁이 구조적으로 사라진다.

## 요구사항·인수 조건

- **FR-19 개정**: "운영 데이터를 매일 자동으로 NAS에 날짜별 사본으로 전송하고 최근 N일치를 보관한다" →
  "운영 데이터의 날짜별 스냅샷을 매일 **로컬에 먼저** 만들고(최근 N일 보관), 위키 저장소의 NAS 동기화 작업이 NAS로
  전송한다. NAS가 일시적으로 끊겨도 로컬 보관 기간 안의 스냅샷은 연결 복구 후 자동으로 전송된다."
- **AC-12 개정**: "백업 작업 실행 후 NAS에 당일 날짜의 DB 사본이 생성되어 있다" → "03:00 백업 후 로컬 `backup/`에,
  03:30 동기화 후 NAS에 당일 날짜의 DB 사본이 있다."
- **AC-28** NAS 연결을 끊은 상태에서도 03:00 백업이 로컬에 성공한다(컨테이너 재시작 없이).
- **AC-29** 부팅 후 컨테이너가 NAS 연결 여부와 무관하게 기동한다.

## 마이그레이션과 롤백

- 컨테이너 재생성 1회(설정 변경). 데이터 변경 없음. NAS에 이미 있는 백업은 그대로 둔다.
- 롤백: 이 커밋을 되돌리고 `.env`에 `HERONGS_BACKUP_MOUNT`를 되살린 뒤 재생성.

## 결과와 단점

- NAS 사본은 최대 하루 늦게(03:30) 올라간다. 로컬 사본이 한 겹 더 생긴다(약 140MB × 14일 ≈ 2GB).
- 컨테이너 안 백업 실패 알림(`backup_failed`)은 로컬 스냅샷 실패만 뜻하게 된다. NAS 전송 실패는 동기화 작업이 따로 알린다.
